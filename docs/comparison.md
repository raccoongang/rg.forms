# Coming from Formik / React Hook Form / TanStack Form

If you build forms with [Formik](https://formik.org/),
[React Hook Form](https://react-hook-form.com/) (RHF), or
[TanStack Form](https://tanstack.com/form/latest), this page shows how the
backend-first approach differs, and measures — with a reproducible script — how
much project-specific code each approach takes for the same feature.

## 1. Backend-first in one minute

React form libraries are **client-side state engines**: the browser owns the
values, per-field touched/dirty state, validation lifecycle, and submission
state, and your server re-validates afterwards. rg.forms inverts that. The
**Python `ReactiveForm` is the single source of truth** — fields, rules,
validation, and initial state live on the server; [Datastar](https://data-star.dev)
provides the client reactivity; and your project owns **one rendering adapter**
for its design system instead of hand-written JSX per form.

> rg.forms does the job of a form library — dynamic, validated, reactive forms —
> the backend-first way: one Python schema, server-authoritative validation, and
> a swappable design-system renderer. You write the schema once, not twice.

## 2. What is being compared

Each scenario below is a **complete vertical slice**: the form schema, its
validation, the rendering, the reactivity, the transport, **and** the server-side
validation and endpoint. A React form without its API handler and server
validation is not equivalent to an rg.forms form, so both are counted.

Line counts are auto-generated by
[`tools/measure_comparisons.py`](https://github.com/raccoongang/rg.forms/blob/master/tools/measure_comparisons.py)
from an explicit [manifest](comparisons/manifest.json); they count non-blank,
non-comment source lines (docstrings and comments excluded). The rg.forms side
of every slice is the **runnable example app**; the competitor side is an
**illustrative fixture** written from official-doc patterns. Full details,
inclusions/exclusions, and honesty rules are in the
[methodology](comparisons/methodology.md).

```bash
python tools/measure_comparisons.py           # regenerate the numbers
python tools/measure_comparisons.py --check    # CI: fail if stale/missing
```

## 3. Results overview

Project-specific source lines per complete vertical slice (non-blank,
non-comment; generated by the script, `2026-08`):

| Scenario | rg.forms | Formik + API | RHF + API | TanStack + API | Fewer lines than client stacks |
|---|---:|---:|---:|---:|---|
| Account registration | **95** | 339 | 365 | 409 | 244–314 (72–77%) |
| Order configurator | **111** | 314 | 281 | 351 | 170–240 (60–68%) |
| Team roster* | **79** | 255 | 230 | 265 | 151–186 (66–70%) |
| Design-system rendering | **94** | 249 | 311 | 270 | 155–217 (62–70%) |

\* rg.forms's slice is **static** rows; the client stacks also implement dynamic
add/remove, which rg.forms does not have yet — see the
[team-roster page](comparisons/team-roster.md).

These are the numbers for *these* implementations, not a universal law
(methodology and caveats: [here](comparisons/methodology.md)). The reduction is
structural, not stylistic — it comes from removing whole layers:

| Architectural fact (per business rule / field) | rg.forms | A client stack + API |
|---|:---:|:---:|
| Places one rule is declared | 1 (Python) | 2 (client schema + server) |
| Files edited to change one rule | 1 | 2 |
| Hand-written client/server transport boundaries | 0 | 1+ |
| Project-specific per-field renderers | 0 (one shared adapter) | 1 per field kind |

## 4. Scenario comparisons

Each scenario has a detailed page with the per-layer breakdown, the equivalent
competitor implementations, and the trade-offs.

- **[Account registration](comparisons/registration.md)** — live username/email
  availability + submit. rg.forms **95** lines vs **339–409**: the client async
  validators, debounce, stale-request handling, error mapping, and the whole
  server tier collapse into `validate_on="blur"` + one `reactive_validate` view,
  with the uniqueness rule written once.
- **[Order configurator](comparisons/order-configurator.md)** — conditional
  fields + exact-`Decimal` pricing. rg.forms **111** vs **281–351**: `watch()`
  conditionals + a re-declared server schema + a client/server total both become
  declarative `visible_when`/`disabled_when`/`computed`, recomputed authoritatively.
- **[Team roster](comparisons/team-roster.md)** — a repeatable section. rg.forms
  **79** (static) vs **230–265** (dynamic): a fair, caveated comparison — the
  client stacks add/remove rows, which rg.forms does not yet.
- **[Design-system rendering](comparisons/design-system-rendering.md)** — one
  form, project styling. rg.forms **94** vs **249–311**: a per-field component
  library versus one shared `field.html` adapter reused by every form.

The [order configurator](comparisons/order-configurator.md) also demonstrates a
rule that has **no client-library equivalent at all**: a computed total the
*server* recomputes exactly and refuses to accept from the client.

## 5. Capability map

Where each rule is enforced today (browser / Datastar / server), after
ADR-0001–0004:

| Capability | rg.forms today |
|---|---|
| Canonical expression semantics | Compiled to JS for the client and re-evaluated on the server from one AST; strict typed equality, numeric-only arithmetic, `/0`→`null` |
| Conditional visibility (`visible_when`) | `data-show` client + hidden fields skipped in server `clean` |
| Conditional requiredness (`required_when`) | reactive `data-attr:required` + enforced in server `clean` |
| Server-authoritative computed fields | live float preview + exact `Decimal` recompute in `clean` (tamper-proof) |
| Static scoped formsets | per-row scoped signals; independent reactivity; prefixed round-trip |
| Multiple prefixed forms per page | independent scopes, no signal collision |
| Declarative incremental validation | `validate_on="blur"`/`"change"` → JSON-signal request + single-field SSE patch |
| Stable a11y ids | `control_id`/`wrapper_id`/`help_id`/`error_id` + `aria-invalid`/`aria-describedby` |
| Design-system overrides | one shared `rg_forms/field.html` adapter; documented context contract |
| External signals | `Meta.external_signals` + `get_external_signal_values()` for client/server parity |

## 6. Honest differences and limitations

- **No client form-state engine**, and no built-in touched/dirty state machine.
  Where a screen wants a `dirty` guard or `submitting` flag, it is a couple of
  Datastar signals, not a subsystem.
- **No dynamic formset mutation yet** — add/remove/reorder rows is out of scope;
  static rows behave independently (see the [team-roster](#4-scenario-comparisons)
  slice, which compares against the competitors' dynamic field arrays honestly).
- **No offline-first forms** or offline persistence.
- **File-field incremental validation is not supported** — files validate on
  submit.
- **External signals used in arithmetic are not statically type-checked** (their
  type is unknown at build time).
- The **browser-level Datastar conformance suite** is a CI responsibility, not
  run in unit tests.
- Rich editors, drag/drop, autocomplete widgets, and highly client-centric
  interactions may still warrant a client component — use rg.forms for the
  server-authoritative core and drop to a component where the interaction needs
  it. The [custom rendering](guide/custom-rendering.md) adapter is that escape
  hatch.

## 7. Choosing between them

**Reach for rg.forms when** the form is fundamentally about capturing and
validating data against server-side rules — most business software. You get one
schema, server-authoritative validation, and reactive UX without a frontend
application, and the rule lives in exactly one place.

**Keep a React form library when** the form itself is the interactive product:
real-time client-only state, offline persistence, heavy client-side computation,
dynamic field-array mutation today, or a component ecosystem you must integrate.
Even then, rg.forms can own the pages that are ordinary forms while the client
library owns the few that are not.

Competitor libraries are excellent at what they are designed for — this
comparison is about **architecture fit**, not quality. Their APIs evolve; the
fixtures record the versions and date (2026-08) they represent.

# Registration comparison

**Requirement:** an account form with live username/email availability checks (as
the user leaves the field), a password-confirmation rule, a business-account
company-email rule, and a final submit — all enforced authoritatively on the
server.

| Form schema + validation | 62¹ | 70 | 71 | 86 |
| Rendering + reactivity | 18 | 121 | 134 | 202 |
| Client transport / async checks | —¹ | 76 | 67 | 48 |
| Backend validation + endpoint | —¹ | 72 | 93 | 73 |
| **Total** | **95** | **339** | **365** | **409** |

¹ In rg.forms the schema, the reactivity, **and** the server validation are the
same `ReactiveForm`; the "view" (15 lines) is the page + the one-line
`reactive_validate` endpoint. There is no separate client schema, no async-check
plumbing, and no second server schema to keep in sync.

## Where the code went

- The client stacks each re-declare the field rules in a schema (Yup/Zod/validators)
  **and** again in `server.py` — two copies of "username must be unique",
  "passwords must match", "business needs a company email".
- Each hand-writes the async availability check: debounce, `fetch`, stale-response
  handling, and mapping the server's `{field: [msgs]}` back onto form state.
- rg.forms declares each rule once (`clean_username`, `clean()`), and
  `validate_on="blur"` generates the request, CSRF header, per-field cancellation,
  pending indicator, and single-field patch. The submit re-runs the identical rules.

## Trade-offs

The client stacks give instant, offline, in-browser validation feedback with no
round-trip; rg.forms's incremental check is a (debounced, cancellable) server
request. For availability/uniqueness that **must** hit the server anyway, this is
the same round-trip either way — but rg.forms does not do purely-client
validation without a request. See the [decision guide](../comparison.md#7-choosing-between-them).

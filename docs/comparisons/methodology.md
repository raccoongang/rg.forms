# Comparison methodology

The comparison pages measure **complete vertical slices** of the same feature,
implemented once with rg.forms and once with each React form library, and count
the project-specific source lines each requires. This page defines exactly what
is measured, what is excluded, and how to reproduce the numbers.

## Why whole slices

A React form component on its own is not comparable to an rg.forms form: the
React form delegates validation and persistence to a server the developer must
also write. To compare like with like, each slice includes **everything the
developer must author to ship the feature**:

- the form schema and its validation rules;
- the rendering (fields, conditional display);
- the reactivity (what recomputes/shows/requires as values change);
- the transport (submit, and any async field checks, with error mapping);
- the **server-side validation** and endpoint.

rg.forms puts almost all of this in one Python class plus a template; a React
library splits it across a client schema, JSX, client transport, and a separate
server that re-declares the rules.

## What is counted

Per slice, the manifest ([`manifest.json`](manifest.json)) lists the exact files
for each layer. The measurement script counts **non-blank, non-comment source
lines** — Python docstrings and JS/TS/HTML comments and header banners are
excluded — so documentation and teaching comments never inflate a number.

**Counted (both sides):** form/schema declaration, validation rules, rendering
markup/components, reactivity wiring, client transport + error mapping, and
server-side validation + endpoint.

**Excluded (both sides), as shared infrastructure amortized across every form:**

- the rg.forms field renderer (`rg_forms/*.html`) — the project writes/overrides
  it **once**; likewise a React project's generic design-system components are
  excluded when the scenario is not specifically about them;
- URL routing / framework router setup;
- React / Vite / Next boilerplate, `package.json`, lockfiles, generated code;
- the rg.forms library itself.

The **design-system-rendering** scenario is the exception: there the per-field
component wiring *is* the subject, so the React field components are counted and
the rg.forms shared adapter's amortized cost is discussed in that page.

## rg.forms slices are runnable; competitor slices are illustrative

The rg.forms side of every slice points at the **real, runnable example app**
under `examples/` (exercised by the example test suite). The competitor side is
an **illustrative fixture** under `fixtures/<framework>/` — idiomatic code
written in our own words from the official documentation patterns, not executed.
This is disclosed on every fixture and in the results. We do not construct an
intentionally poor competitor implementation; where a stack can share a schema
between client and server, the fixture and the prose say so.

## Architectural counts

Line counts are one lens; the structural facts are often more telling and are
declared per slice in the manifest (not auto-derived from source):

- **transport boundaries** — network request/response mappings the developer
  hand-writes (client transport + server endpoint pair). rg.forms's normal
  Django POST and its *generated* incremental-validation request are 0
  hand-written boundaries; a SPA has 1+.
- **rule declaration sites per rule** — how many places one business rule is
  written. rg.forms: 1 (Python). Client-lib + API: 2 (client schema + server).
- **rule change sites per rule** — how many files you edit to change one rule.
- **project-specific field renderers** — bespoke per-field components the
  project maintains (0 for rg.forms's shared adapter).

## Reproducing the numbers

```bash
python tools/measure_comparisons.py           # regenerate measurements.json
python tools/measure_comparisons.py --check    # CI: fail if stale or files missing
```

The script fails if any manifest-referenced file is missing, so the results
cannot silently drift from the fixtures. Results are written to
[`measurements.json`](measurements.json) and surfaced on the
[comparison page](../comparison.md).

## Honesty rules

- Numbers describe **these implementations**, not a universal law: we say "in
  this vertical slice," never "always fewer lines."
- Every percentage names its scenario and is generated by the script above.
- Competitor framework names link to their official docs; fixtures record the
  library versions and the date (2026-08) they represent. Framework APIs evolve;
  the measurements reflect the pinned patterns.
- Competitor libraries are excellent at what they are designed for — client-side
  form state. The comparison is about *architecture fit*, not quality.

Risks and Considerations

Understanding trade-offs before adopting rg.forms

rg.forms offers significant productivity gains, but like any technology choice, comes with trade-offs. This page documents known risks and our mitigation strategies.

High Risk

Datastar Dependency

Risk: Datastar reached stable 1.0 and rg.forms pins the exact signed tag @v1.0.2, but it still has a smaller community than HTMX or Alpine. If the Datastar API changes significantly or the project becomes unmaintained, rg.forms is tightly coupled.

Mitigation:

  • Expression evaluator is backend-only (Python) - not Datastar-dependent
  • Frontend attributes (data-show, data-bind) could be adapted to HTMX + Alpine
  • Monitor Datastar project health and community growth
  • Core value (single source of truth) is framework-agnostic

API Stability

Risk: Field attributes have grown significantly and more will likely be needed as real-world usage reveals gaps:

  • Current: visible_when, required_when, computed, disabled_when, read_only_when, help_text_when, placeholder_when, min_when, max_when, validate_on, debounce, depends_on, choices_from...
  • Potential: error_message_when, css_class_when, choices_when

Mitigation:

  • Semantic versioning with clear deprecation policy
  • Collect real-world usage feedback before stabilizing API
  • Breaking changes only in major versions with migration guides

Medium Risk

Missing Django Integrations

Risk: Some common Django patterns are not yet supported:

  • ReactiveModelForm - most common use case
  • Dynamic formset mutation (add/remove/reorder rows) — static formsets are supported and fully reactive per row (ADR-0003)
  • FileField with upload progress
  • crispy-forms integration

Mitigation: Prioritize ReactiveModelForm next; dynamic-formset mutation is server-driven (a small Datastar handler) until a declarative helper lands. Document workarounds.

Expression Errors (largely addressed — ADR-0002 §5)

Was: typos in expressions ($ordertpye instead of $order_type) failed silently, defaulting to visible.

Now:

  • A Django system check (rg_forms.W001) validates every expression at build time — unknown references, string/boolean operands in arithmetic, and array-field references are flagged before runtime.
  • Runtime evaluation errors are logged (to the rg.forms logger), not silently swallowed, and remain fail-open so a broken rule never hides a field or drops a value.
  • A falsy result now correctly hides/de-requires a field (distinct from an evaluation error) — matching the client.

Residual: runtime errors are still fail-open by design; the build-time check lands as a warning to ease adoption (graduating to an error later).

No IDE Support for Expressions

Risk: Expression strings like "$order_type == 'urgent'" have no autocomplete, type checking, or refactoring support.

Mitigation: Document syntax clearly. Consider future TypedDict approach. Provide testing utilities.

Lower Risk

Expression language is a small, stable subset (by design)

The reactive DSL is intentionally small and portable. Since ADR-0002 it has rigorous, conformance-tested semantics that are identical on the client and the server (strict typed equality, numeric-only arithmetic, /0 → null). It covers the conditional visibility/requiredness and computed arithmetic that most business forms need.

Deliberately out of scope in v1 (for cross-runtime portability): functions (len(...)), ternaries ($a ? $b : $c), array indexing/methods ($items[0], .length), string methods (contains), and author-level nested paths ($address.city). This is a scoping decision, not instability.

Escape hatch: anything beyond the DSL goes in an ordinary clean_*() / clean() method — full Python, server-authoritative. Array operations may arrive later with explicitly defined cross-runtime semantics.

Single CSS Framework

Only Bulma reference templates ship. The rendering layer is design-system-agnostic (ADR-0001) — override rg_forms/field.html once for your design system; see the Design-System Override example.

Performance at Scale

Reactive UX runs client-side; only cascading choices and incremental validation take a server round-trip, debounced and (for validation) per-field cancellable.

When NOT to Use rg.forms

rg.forms (and a Datastar-first architecture generally) fits most web forms. Reach for a client framework when the screen is a genuinely standalone client application:

  • Offline / local-first - must work, and hold state, without the server
  • Genuinely client-bound UI - canvas/WebGL, rich in-browser editors, high-frequency local animation
  • React Native code sharing - the same form logic must run on web and native mobile
  • Existing SPA ecosystem - you must integrate with an established React/Vue app and its components

Interactions often assumed to need a client framework — multi-step wizards, dependent selects, live totals, and add/remove/reorder rows (drag-and-drop included) — are all doable server-driven with Datastar, and usually the split is per-page, not per-app.

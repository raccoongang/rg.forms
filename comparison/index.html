    Coming from Formik / React Hook Form / TanStack Form¶

    If you build forms with Formik, React Hook Form (RHF), or TanStack Form, this page shows how the backend-first approach differs, and measures — with a reproducible script — how much project-specific code each approach takes for the same feature.

    1. Backend-first in one minute¶

    React form libraries are client-side state engines: the browser owns the values, per-field touched/dirty state, validation lifecycle, and submission state, and your server re-validates afterwards. rg.forms inverts that. The Python ReactiveForm is the single source of truth — fields, rules, validation, and initial state live on the server; Datastar provides the client reactivity; and your project owns one rendering adapter for its design system instead of hand-written JSX per form.

    rg.forms does the job of a form library — dynamic, validated, reactive forms — the backend-first way: one Python schema, server-authoritative validation, and a swappable design-system renderer. You write the schema once, not twice.

    2. What is being compared¶

    Each scenario below is a complete vertical slice: the form schema, its validation, the rendering, the reactivity, the transport, and the server-side validation and endpoint. A React form without its API handler and server validation is not equivalent to an rg.forms form, so both are counted.

    Line counts are auto-generated by tools/measure_comparisons.py from an explicit manifest; they count non-blank, non-comment source lines (docstrings and comments excluded). The rg.forms side of every slice is the runnable example app; the competitor side is an illustrative fixture written from official-doc patterns.     4. Scenario comparisons¶

    Each scenario has a detailed page with the per-layer breakdown, the equivalent competitor implementations, and the trade-offs.

    • Account registration — live username/email availability + submit. rg.forms 96 lines vs 339–409: the client async validators, debounce, stale-request handling, error mapping, and the whole server tier collapse into validate_on="blur" + one reactive_validate view, with the uniqueness rule written once.
    • Order configurator — conditional fields + exact-Decimal pricing. rg.forms 113 vs 281–351: watch() conditionals + a re-declared server schema + a client/server total both become declarative visible_when/disabled_when/computed, recomputed authoritatively.
    • Team roster — a repeatable section. rg.forms 79 (static) vs 230–265 (dynamic): a fair, caveated comparison — the client stacks add/remove rows, which rg.forms does not yet.
    • Design-system rendering — one form, project styling. rg.forms 82 vs 249–311: a per-field component library versus one shared field.html adapter reused by every form.

    The order configurator also demonstrates a rule that has no client-library equivalent at all: a computed total the server recomputes exactly and refuses to accept from the client.

    6. Honest differences and limitations¶

    • No client form-state engine, and no built-in touched/dirty state machine. Where a screen wants a dirty guard or submitting flag, it is a couple of Datastar signals, not a subsystem.
    • No dynamic formset mutation yet — add/remove/reorder rows is out of scope; static rows behave independently (see the team-roster slice, which compares against the competitors' dynamic field arrays honestly).
    • No offline-first forms or offline persistence.
    • File-field incremental validation is not supported — files validate on submit.
    • External signals used in arithmetic are not statically type-checked (their type is unknown at build time).
    • The browser-level Datastar conformance suite is a CI responsibility, not run in unit tests.
    • Genuinely client-bound widgets — rich in-browser editors (WYSIWYG, code, canvas/WebGL), high-frequency local animation — may still warrant a client component. (Common interactions often assumed to need one — drag-and-drop reordering, autocomplete, dependent selects, live totals — are all doable server-driven with Datastar.) Use rg.forms for the server-authoritative core and drop to a component only where the interaction genuinely needs it; the custom rendering adapter is that escape hatch.

    7. Choosing between them¶

    The honest default for most web applications is server-driven, Datastar-first: render on the server, let Datastar push updates over SSE, and ship a few kilobytes of JavaScript instead of a client application. rg.forms is the forms layer of that architecture — your rules live once in Python, the browser reflects them for UX, and the server stays authoritative.

    Default to the Datastar-first approach for the software most teams actually build: CRUD, dashboards, onboarding and configuration flows, wizards, admin and back-office tools, content and commerce. This now covers much of what was once assumed to require an SPA — conditional and computed forms (this library), server-pushed live updates, and even real-time collaborative views. Anders Murphy's one-billion-checkboxes demo is an existence proof: a real-time, collaborative, high-cardinality UI built with Datastar + SSE and no client framework (its author is candid that it is a demonstration, not a tuned benchmark — treat it as "this is possible," not a throughput guarantee). A maintenance argument compounds the point: server templates stay backward-compatible for years, while client frameworks tend to churn through rewrites every few years (longer argument).

    Reach for a React/SPA framework (and its form library) when the app is a genuinely standalone client application — not a server-rendered site with reactive pieces:

    • offline-first / local-first behavior, or long-lived client state that must survive without the server;
    • heavy client-side computation or rendering (canvas/WebGL, spreadsheets, live editors, diagramming);
    • genuinely client-bound interaction: canvas/WebGL surfaces, rich touch-gesture or direct-manipulation UIs, high-frequency local animation;
    • an existing SPA or component ecosystem you must integrate with.

    Note what is deliberately not on that list: dynamic add / remove / reorder of rows — including drag-and-drop reordering. None of that is a Datastar limitation; it is a natural server-driven interaction — a small handler posts the action (or the new order) and the server re-renders the affected rows over SSE (Murphy's demo mutates a billion cells exactly this way). rg.forms simply does not yet ship a declarative helper for it, so today you write that handler yourself — still server-driven, still less code and more performant than adding a client framework. The missing piece is a library convenience, not an architectural reason to reach for an SPA.

    Even then the split is usually per page, not per app: the ordinary forms and pages stay server-driven with rg.forms, and a client component owns only the few screens that are truly interactive products.

    React form libraries are excellent at what they are designed for — client-side form state — and this comparison is about architecture fit, not quality. The substantive claim is only that far fewer applications need that client engine than the current default assumes. Their APIs evolve; the fixtures record the versions and date (2026-08) they represent.
